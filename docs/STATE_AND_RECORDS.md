# State and Records

Preserve relations that let another receiver understand the present and
continue correctly. Use selected private storage and existing native records
where they suffice.

These are flexible semantic contracts and fictional reference examples.
They prescribe no universal database, mandatory schema or file layout.
A short note, linked thread or existing project record may serve better than
another table.

## Separate current view, evidence and method

| Kind | What it owns |
| --- | --- |
| Current entry | Purpose, material present, open reason and next trigger |
| Source | Product/research fact, attributed direction or originating meaning |
| Creative artifact | Actual copy/media, editable source when available, selected revision and its source/inspection relation |
| Effect record | Action occurred, attempted or still unexecuted |
| Observation | Who inspected what, when, with which coverage and limitation |
| Consequence | Observed difference and qualified interpretation |
| Relationship | Current relation and next trigger owner |
| Competence | Reusable method and why it should change later work |
| Receiver binding | Actual means, persistence, controller and authority |

A current view can point to these without copying them. Product CURRENT is not
a populated user field. Do not replace local state when updating public methods.

## Current field

Carry enough to answer:

- What purpose or movement is selected, and by whom?
- Which source, event, correction or consequence changed the present?
- What happened, what remains uncertain and what is only proposed?
- Which owner or competence is needed next?
- What trigger, reason or stop condition makes continuation useful?
- Where are the source, evidence and actual receiver bindings?

Preserve attribution. “The receiver proposes a beginner-focused introduction”
differs from “The operator selected beginners.” If they were substituted,
repair the present and the entry that replays it; preserve earlier occurrence.

Keep an approved aspect, a candidate revision and a separate experiment distinct.
A more recent visual experiment does not automatically replace the selected
post asset; appreciation of its style does not approve its message or use.

For creative work, keep the actual files reachable from that selection. The
[media production and continuity method](../skills/social-media-composition/references/production-and-continuity.md)
connects source, master or input assets, production instruction, inspected
revision, useful alternatives and selected output. Use the existing record
that can carry these relations. A later source or audience change should make
the dependent artifacts identifiable without replacing valid unrelated work.

An old product version, later conversation and expired permission do not
necessarily belong to one present. Time and applicability matter when they
change the decision.

## Effects and uncertain occurrence

A fictional record could be:

~~~yaml
effect: forum-answer-17
target:
  surface: example developer forum
  acting_identity: user-selected local account
  object: exact thread reference retained privately
action:
  kind: reply
  revision: r2
  content_reference: private final body
  assets: none
authority:
  source: current local policy reference
  scope: bounded replies in the selected project
controller: receiver-beta
disposition: outcome_uncertain
attempt:
  observed_at: T1
  evidence: request returned before native result was visible
native_receipt: unknown
source_persistence: attempted-effect record retained
next:
  action: inspect native thread before retry
  reason: occurrence may already have happened
~~~

Use an identifier, digest or native link when it distinguishes the action.
A digest establishes equality of represented bytes, not authorship, truth,
approval or occurrence.

Dispositions may include proposed, waiting for approval, selected, superseded,
attempted, outcome uncertain, occurred or held. Use what fits; do not force
every action through every state.

If the reply is found, record native identity, body comparison, time, source and
controller. The receipt resolves occurrence; it does not justify another send
or prove usefulness.

## Consequences and time

Keep four layers distinguishable where they differ:

~~~yaml
event:
  fact: a fictional feature announcement was published
  evidence: native identity and original body
then:
  source: version A still offered the feature
  understanding: announcement described present availability
later_observation:
  at: T2
  source: current product owner
  fact: feature withdrawn in version B
now:
  interpretation: queued availability claims no longer apply
  action: requalify dependent drafts and current reader guidance
  uncertainty: earlier reader reliance is unknown
~~~

A later correction appends a relation. It does not fabricate that the earlier
actor knew a future fact.

Keep no_change scoped: “no replies visible in the loaded native thread at T3”
is narrower than “nobody replied.” A receipt read today retains its original
observation time.

Metrics keep their meaning. Reported impressions remain the platform's exposure
metric; a reply is a conversational event; author-reported testing remains a
report until examined.
Temporal sequence is not causal proof.

## Relationships

A fictional continuation might say:

~~~yaml
counterpart: maintainer resolved from the exact discussion
relation: independent technical feedback
last_material_event: they will return if a public reproduction is available
state: deferred
next_trigger_owner: counterpart
local_action: wait
reopen_when: a materially relevant event changes the relation
source: exact attributed statement retained privately
~~~

No reply, defer and closure imply different next moves. A connection does not
establish commercial fit, private-message authority or unrelated outreach consent.

Retain discovery provenance when relevant. If it was not preserved, do not
invent it afterward.

## Reusable learning

A learning return should make later work possible or better:

~~~yaml
observed_difference: draft survived after its source claim was withdrawn
prior_method: prepare from release note and replay the body later
changed_method: reenter current claim owner before the dependent write
owner: local effect-formation competence
entry_changed: queue route now reaches current source applicability
next_non_identical_use: different discussion depends on changed compatibility claim
evidence_state: method revised; later use not yet observed
~~~

A log alone is not an evolved method. If know-how existed but was not reached,
correct entry/discovery. If shallow, deepen the body that must act. If several
owners need to change, preserve distinct returns and their interface.

Use [competence evolution](../skills/social-competence-evolution/SKILL.md) and
[EVOLUTION](../EVOLUTION.md) for material method or kernel change.

## Private context and persistence

Keep identities, accounts, communications, contacts, approvals, unpublished
strategy and sensitive context in the selected private instance. Give a surface
only the context pertinent to its action.

Public examples teach relations using fictional data. They do not carry a real
user's approvals, accounts, receipts or viewpoint as product defaults.

If persistence is unavailable, state what is session-local and offer a
recoverable handoff through available means. A proposed record printed in chat
does not establish durable continuity.
