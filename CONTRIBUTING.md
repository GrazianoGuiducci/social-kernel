# Contributing to Social Kernel

Social Kernel is a public development project. The most useful contributions come from real use: a receiver enters a real situation, something material happens, and the result exposes a correction, reusable method, missing capability or useful `no_change`.

You do not need to prove the whole kernel before contributing.

## Useful contributions

Open an issue, discussion or pull request when you have one of these:

- **Field report.** Describe the real situation, source revision, receiving environment, what the kernel changed in the work and what you actually observed.
- **Method correction.** Identify the source, object or relation that the current method distorted or failed to reach, and the smallest reusable correction.
- **New reusable capability.** Show why an existing competence cannot carry the function before proposing another competence.
- **Receiver or packaging fix.** Separate source availability, package construction, installation/discovery and actual exercised behavior.
- **Documentation improvement.** Make the method easier to understand or adopt without weakening its source boundaries.

A useful report can end in `no_change`. The goal is not to manufacture novelty.

## Preserve the evidence boundary

State only what the contribution actually establishes.

A source file being present does not prove native host discovery. A generated artifact does not prove audience impact. A successful local use does not prove universal adoption. A scheduled configuration does not prove a wake occurred.

Mechanical checks are welcome when they materially apply to a code or packaging change, but contributors do not need to run artificial behavioral tests merely to create evidence.

## Keep private fields private

Do not submit credentials, account state, private conversations, unpublished strategy, personal contacts or a user's private continuity field.

Generalize reusable learning before moving it into the public product. Preserve enough provenance to explain the relation without copying private operating state.

## Pull requests

Keep changes bounded to the owner that should behave differently. Preserve valid prior work and historical evidence. If a change modifies a method, make the next consumer able to reach it. If it only records an event, do not turn the event into a universal rule.

For material source changes, explain:

1. the situation or source that exposed the difference;
2. what changed and why;
3. which owner or competence carries the change;
4. what was actually checked or exercised;
5. what remains unobserved.
